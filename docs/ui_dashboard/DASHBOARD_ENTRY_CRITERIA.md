# Dashboard Entry Criteria

## Prerequisites

All of the following must be complete before the first dashboard implementation begins:

### 1. CA-7 Passed

The CA-7 Controlled Adaptive gate must be passed. The closeout report must exist and show all criteria met.

### 2. Security Checker Passing

The security checker must pass with no critical findings. All security checks in `docs/security/` must show pass or warn (no fail).

### 3. CI Passing

CI must pass on the main branch. All tests must pass. No failing workflows.

### 4. Packaging Complete

The packaging design and implementation must be complete. The harness must be packageable and distributable.

### 5. Provider Integration Designed

The provider integration design must exist in `docs/provider_integration/`. The design must specify supported providers, credential management, and API contract.

### 6. Sandbox Execution Designed

The sandbox execution design must exist in `docs/sandbox_execution/`. The design must specify execution model, isolation boundaries, and security constraints.

### 7. UI Dashboard Design Complete

All 6 design documents in `docs/ui_dashboard/` must be complete and approved:
- `README.md`
- `UI_DASHBOARD_DESIGN.md`
- `DASHBOARD_DATA_CONTRACT.md`
- `READ_ONLY_INTERACTION_POLICY.md`
- `DASHBOARD_SECURITY_AND_PRIVACY.md`
- This document (`DASHBOARD_ENTRY_CRITERIA.md`)

### 8. Human Approval

A human stakeholder must approve the dashboard design and entry criteria. This approval must be recorded in the governance workflow.

### 9. Data Contract Approved

The data contract in `DASHBOARD_DATA_CONTRACT.md` must be approved. All data sources, schemas, and redaction rules must be validated.

### 10. Redaction Policy Approved

The security and privacy policy in `DASHBOARD_SECURITY_AND_PRIVACY.md` must be approved. All redaction rules and display policies must be validated.

## Allowed First Implementation

With all prerequisites met, the first implementation may proceed as:

### Static Report

A generated markdown or HTML file containing:
- Gate status summary
- Eval results summary
- Security check summary
- Cost estimates (redacted)
- Track status

Generated by a script that reads data sources and outputs a static file. No server. No runtime.

### Local HTML File

An HTML file that:
- Is opened directly in a browser (file:// protocol)
- Reads data from embedded JSON or inline data
- Renders dashboard views with plain HTML/CSS/JS
- Has no external dependencies
- Makes no network requests
- Writes no data

## Forbidden First Implementation

The following are explicitly forbidden for the first implementation:

### Web Server

No HTTP server, no Express, no Flask, no FastAPI, no server of any kind.

### Hosted Deployment

No deployment to Vercel, Netlify, AWS, GCP, or any cloud platform.

### Authentication System

No login, no OAuth, no JWT, no session management.

### Database

No PostgreSQL, no SQLite, no Redis, no database of any kind.

### Telemetry

No analytics, no tracking, no external logging.

### Write Capability

No state mutation through the dashboard. No policy activation, no task editing, no event logging.

### Provider Calls

No LLM API calls through the dashboard. No model inference.

### Sandbox Execution

No code execution through the dashboard.

### Policy Activation

No policy lifecycle management through the dashboard.

### PR Creation

No git operations through the dashboard.

## Validation Checklist

Before implementation begins, verify:

- [ ] CA-7 closeout report exists and shows passed
- [ ] Security checker results show no critical failures
- [ ] CI is passing on main
- [ ] Packaging design exists and is implemented
- [ ] Provider integration design exists
- [ ] Sandbox execution design exists
- [ ] All 6 dashboard design docs exist and are complete
- [ ] Human approval recorded in governance workflow
- [ ] Data contract approved
- [ ] Redaction policy approved
- [ ] No frontend dependencies in package.json or equivalent
- [ ] No server code in the repository
- [ ] No network calls in the dashboard code

## Scope

This document defines the entry criteria for the first implementation only. Subsequent versions (interactive mode, server-based, multi-user) require separate entry criteria documents with their own prerequisites and approval processes.
