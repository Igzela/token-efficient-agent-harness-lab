## Three Comparison Dimensions

Every experimental arm binds all three identities even while a stage varies only one dimension:

```text
ExperimentArm
= HarnessImplementation
x ModelPlan
x StrategyPlan
x task/corpus/evaluator/budget/seed/environment bindings
```

| Dimension | Compared object | Included examples | Never implied |
|---|---|---|---|
| Harness | A complete agent harness implementation and its planning/tool loop | accepted Native harness; later admitted Codex, Claude Code, Pi, OpenCode, LangGraph-based, or other harness implementations | A CLI transport alone is not the Harness identity; admission never transfers Rust/store/evaluator authority |
| Model | Model/provider/role assignment and routing topology | direct, role-separated, ordered fallback, panel/judge/synthesizer fusion | Model routing does not prove delivered quality and cannot own ProductTask budget |
| Strategy | Prompt, context, memory, skill, tool, retry, and compression policy | baseline context, CWS, memory-only, skill-only, bounded combinations | A strategy cannot change evaluator, labels, authority, safety, budget, or adoption |

A Harness implementation may communicate through a CLI, API, subprocess, or library, but that transport is internal to the implementation. The compared top-level object is the complete harness behavior behind the shared run seam. The Rust engine remains the sole admission, scheduler, workspace, budget, verification, evidence, output, audit, recovery, and persistence authority; `LocalProductStore` remains the sole application-owned store.

The high-level seam is introduced only when C1 has two admissible Harness implementations. C0 uses the accepted single implementation directly rather than creating a hypothetical one-adapter abstraction. At C1 promotion, the planning owner must decide whether the current executor seam can be deepened or a higher-level seam is required. Either choice exposes one small interface whose observable result includes terminal state, verified deliverable, normalized usage/cost, failures/missingness, cleanup, and recovery evidence.

External-framework reuse is Harness-first, not CLI-first. C1 audits the complete candidate at an exact commit/version, license/SBOM/provenance, tool and state loop, model routing, workspace/process confinement, usage observability, cancellation/cleanup/restart, artifact/output semantics, and untrusted-code threat boundary. It records exactly one `EMBED_BEHIND_SEAM`, `CONFINED_SUBPROCESS`, `POLICY_BLOCKED`, `CAPABILITY_BLOCKED`, `INCOMPARABLE`, or `REJECT` disposition. An admitted open-source Harness may be reused substantially behind the shared seam; it need not be rewritten as a thin CLI adapter. Admission still cannot transfer the Rust engine's outer scheduling, policy, budget, verification, evidence, persistence, output, audit, or rollback authority.

Equivalent implementation means identical external acceptance conditions at that seam, not identical internal code. A matrix cell that cannot satisfy the same task, evaluator, budget, evidence, and outcome contract is `INCOMPARABLE`; it is not forced into an independence or interaction claim.

## Closed-Loop Evidence Contract

Every stage reuses the existing Product Golden Path and evidence owners:

```text
ProductTask + source/worktree binding
-> admitted HarnessImplementation(ModelPlan, StrategyPlan)
-> bounded repository work
-> fixed verification
-> artifact/output candidate
-> terminal evidence + ExecutionUsageEventV1
-> scorecard/VDE + lifecycle-cost reconciliation
-> independent closeout
```

The measurable outcome is verified delivered work, not token count alone. Total lifecycle cost includes generation, failed attempts, diagnosis, hypotheses, review, repair, CI, recovery, cleanup, human effort, and any stronger-model escalation. Unavailable or ambiguous cost is explicit and never zero. A weak-agent arm includes the cost of any rescue needed to make it pass; hidden strong-model rescue invalidates attribution.

RWE supplies task/corpus/evidence inputs to this loop rather than a competing runtime. CWS, memory, and skills are Strategy variants. Direct/fallback/fusion are ModelPlan variants. Evidence-insufficient experimental variants may enter a later frozen comparison as `EXPERIMENTAL` arms, but remain default-off and gain no adoption authority merely by joining the loop.

Package compression never permits a worker to jump to a later card, package, matrix rung, generation, or transfer phase merely because earlier local files exist.

## Adoption and Claim Boundary

| Evidence or decision | Does not imply |
|---|---|
| candidate generation | causal explanation or prediction accuracy |
| prediction accuracy | verified delivery or selection authority |
| verified delivery | experimental parent selection or transfer |
| experimental selection | sealed-transfer acceptance or active-Harness adoption |
| transfer acceptance | human adoption, improvement-operator support, release, or deployment |

A GO authorizes only its exact named next action. `CONTROLLED_FAILURE`, `PARTIAL_COMPARISON`, `INCOMPARABLE`, `NO_GO`, `DECLINE`, `DEFER`, `SATURATED`, `HARM`, `INSUFFICIENT`, and `OUTCOME_UNKNOWN` remain first-class dispositions. None may be suppressed to keep the spiral moving.
